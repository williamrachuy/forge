# Multi-node compute for Forge sim workloads

**Status:** ACTIVE (2026-07-27). Tooling: `tools/simstats/forge_nodes.sh`, roster:
`tools/simstats/nodes.conf`.

**Read this before running anything across machines.** The tooling is easy; the correctness rules
are the part that will silently ruin an experiment if ignored.

---

## 1. Why this exists

Throughput is the binding constraint on the entire post-V0 Ultron roadmap. Expert iteration,
depth-1 search, and the Tier-1 stochastic-policy/league work in `ULTRON_THEORY_OF_MIND_STUDY.md`
all need *more* games per round than the last, and every round pays the cost again.

TICKET-V4-022 removed the single biggest tax (a static-map leak pinning every simulation copy —
~5x throughput). Adding a second machine is the next increment, and unlike the leak fix it is
purely additive: it costs nothing in correctness *provided the rules in §3 are followed*.

The second machine also has a non-throughput purpose William named explicitly: **keeping the
laptop usable.** A 5-hour corpus run pins 2 cores and 12GB on the primary box. Moving it off is
worth doing even when it does not shorten the wall clock.

---

## 2. The nodes

| node | host | cores | RAM | safe workers | role |
|---|---|---|---|---|---|
| **dell-xps15** | local | 8 | 31 GB | 2 × 6g | primary — builds, gates, training, interactive |
| **asus-vivopc** | `asus-vivopc` | 4 (i5-6400 @ 2.7GHz) | 15 GB (~9 free) | 1 × 4g | generation only |

**asus-vivopc is materially slower, and the reason is RAM, not cores.** Measured on a 4-game smoke
(2026-07-27, commit `90cff9023a`): at 1×6g the box hit 12.0 GB / 15.9 GB used with 951 MB swapped,
and the **first game took 257.8 s** against this laptop's 21 s median. Once warm, the second game
took **24.4 s** — competitive. So the profile is *high variance with a bad cold start under memory
pressure*, not uniform slowness. `xmx` was lowered 6g → 4g to keep the heap off swap.

Plan for **~60–100 games/hour** against dell-xps15's ~186, i.e. a useful *addition* of roughly
+30–50% aggregate, not a replacement. Long runs amortise the cold start; short ones do not, which
is the concrete reason for the >2 hour threshold in §5.

`workers`/`xmx` in `nodes.conf` are the **safe** numbers, not the maximum. Do not raise them
without re-measuring free RAM on that box first.

## 3. The rules (this is the important section)

### 3.1 Seed disjointness — the #1 hazard
Two nodes running the same config with the same seed generate **the same games**. You get a corpus
that looks twice as big and contains half as much information, and a win rate computed over
duplicated samples with a falsely narrow confidence interval.

`forge_nodes.sh offload` allocates seed ranges **10,000,000 apart per node**, far wider than any
run consumes. If you launch nodes by hand, you own this: give every node a distinct `seed_base`.
(Related prior scar: the harness must not use `run.repeat`, which re-runs identical seeds — see
`run_gate_v4_016.sh`'s header.)

### 3.2 Same commit, or results are not comparable
`forge_nodes.sh run` **refuses to launch** if the node's `git rev-parse HEAD` differs from local.
This is not bureaucracy: this project has already lost a full experiment to a stale jar (see the
BUILD TRAP section in `FORGE_TRACKER.md`), and a mixed-commit corpus is worse — it is silently
half-generated by a different AI.

### 3.3 The BUILD TRAP applies per node
`mvn test` does not rebuild the shaded jar the simulator runs, and **each machine has its own
jar**. `forge_nodes.sh sync <node>` pushes the commit *and* rebuilds. Syncing the commit alone is
not enough and is exactly the failure mode that produced a zero-output run in V4-006.

### 3.4 What may be offloaded

| workload | offload? | why |
|---|---|---|
| **corpus / data generation** | **YES** | embarrassingly parallel over disjoint seeds; a slow node still contributes; the round harness already treats shards independently |
| smoke tests, monster diagnostics | YES | throwaway; only need to complete |
| **win-rate GATES** | **NO — default** | see below |
| NN training | NO | minutes of CPU on the primary; torch venv lives there |
| builds | N/A | must happen on every node that runs sims |

**Why gates must not be split across nodes.** A gate is a *measurement*, and its baseline was
measured on specific hardware. V0's 28.5% baseline (n=1083) was measured on dell-xps15. Hardware
should not change a win rate in principle — but this project has been burned repeatedly by
confounds that "shouldn't matter" (a pruning change, a corpus-size change, a randomly-initialised
aux head), and every one cost a re-run to disentangle. Timeouts in particular are wall-clock
bounded (`timeoutSeconds=360`), so **a slower node genuinely does time out more often**, and
timeout exclusions bias win rate (that is TICKET-V4-021's whole finding).

A gate may run on asus-vivopc only if the **entire** gate *and* its comparison baseline ran there.
Never split one gate across two machines.

### 3.5 Provenance
`forge_nodes.sh collect <run>` pulls remote output into
`simstats/out/<run>/nodes/<node>/`, so which machine produced which games stays explicit and
auditable after the fact. Local-node output stays at `simstats/out/<run>/`.

## 4. How to use it

**Use `forge.sh`. It is the orchestration layer; `forge_nodes.sh` is the plumbing underneath it.**
The point of `forge.sh` is that you should never have to remember a sequence of steps, and never
have to read raw logs to know whether things are healthy. Each command prints a compact PASS/FAIL
block and returns a meaningful exit code (0 ok, 1 failure, 2 usage, 3 needs a commit first).

```bash
# Is everything healthy? (commit, jar, model, RAM, disk, idle) — one screen, all nodes
bash tools/simstats/forge.sh doctor [<model.bin>]

# Bring every node to a launchable state. Idempotent and SELF-REMEDIATING: syncs commits,
# waits for the rebuild, copies the model. Refuses (exit 3) if the config is uncommitted.
bash tools/simstats/forge.sh preflight <config.ini> <model.bin>

# The one command you actually want: preflight + split launch + VERIFY the net really loaded
bash tools/simstats/forge.sh generate <config.ini> <total_games> <run_name> <model.bin>

# Aggregate status across every node: games, timeouts, win rate + CI, median game, state
bash tools/simstats/forge.sh status <run_name>

# Block until every node is idle, then print the summary
bash tools/simstats/forge.sh wait <run_name>

# Gather results AND verify the seed-disjointness rule actually held (§3.1)
bash tools/simstats/forge.sh collect <run_name>

bash tools/simstats/forge.sh stopall
```

**Why `generate` verifies rather than trusts.** The NN model is gitignored, so a `sync` cannot carry
it; and if `ULTRON_NN_MODEL_PATH` is unset the JVM logs "neural eval unavailable" and **silently
falls back to the heuristic AI** — producing a corpus with no network in it, with no crash and no
warning. `generate` therefore greps every node's log for `NeuralStateEvaluator: loaded model` and
fails loudly if any node is missing it. Same reasoning as the BUILD TRAP: on this project the
dangerous failures are silent-and-wrong, not loud-and-broken.

**Why `collect` verifies rather than trusts.** It counts distinct `gameSeed`s across all collected
files. Duplicates mean two nodes shared a seed range, which inflates corpus size and narrows
confidence intervals on *duplicated* samples. §3.1 is a rule; this is the check that it held.

### Lower-level plumbing (`forge_nodes.sh`)

Prefer `forge.sh`. Reach for these only when doing something the orchestrator does not cover.

```bash
# What's out there, are nodes on my commit, is anything already running?
bash tools/simstats/forge_nodes.sh status

# Push current commit to a node and rebuild its jar (do this after ANY code change)
bash tools/simstats/forge_nodes.sh sync asus-vivopc

# Split a generation target across all nodes, weighted by workers, disjoint seeds
bash tools/simstats/forge_nodes.sh offload configs/simstats/<cfg>.ini 1500 v4_0xx_corpus

# Or target one node explicitly
bash tools/simstats/forge_nodes.sh run asus-vivopc configs/simstats/<cfg>.ini 500 v4_0xx_corpus 40000000

# Pull results back with node provenance
bash tools/simstats/forge_nodes.sh collect v4_0xx_corpus

# Stop a node's run
bash tools/simstats/forge_nodes.sh stop asus-vivopc
```

Every run — local or remote — gets a watcher at the top level of its output directory
(`bash simstats/out/<run>/watch.sh`); see the watcher section in `FORGE_TRACKER.md`. On a remote
node: `ssh asus-vivopc 'bash ~/github/forge/simstats/out/<run>/watch.sh'`.

## 5. When to offload *without being asked*

An agent may offload on its own initiative when **all** of these hold:

1. The workload is **generation, not measurement** (§3.4) — corpus, smoke, diagnostic.
2. Estimated wall clock on the primary alone is **> ~2 hours**. Below that, setup and collection
   overhead dominate and the split is not worth the added moving parts.
3. `forge_nodes.sh status` shows the target node **reachable, on the same commit, with a built
   jar, and 0 running sims**.
4. Nothing on the primary needs the freed capacity more urgently.

Otherwise **ask first**. In particular, always ask before:
- offloading anything whose output feeds a **published number** (any gate),
- changing `workers`/`xmx` in `nodes.conf`,
- anything that would leave a run on a remote box unattended without a watcher.

Say plainly which node each result came from when reporting. A number without its machine is a
number that cannot be reproduced.

## 6. Bootstrap notes (how asus-vivopc was set up, for adding a third node)

1. SSH from the primary must work key-only: `ssh -o BatchMode=yes <host> true`.
2. Repo at `~/github/forge` on the same branch.
3. **Push directly, primary → node**, no GitHub round trip:
   ```bash
   ssh <host> 'cd ~/github/forge && git config receive.denyCurrentBranch updateInstead'
   git remote add <node> <host>:/home/william/github/forge
   git push <node> <branch>
   ```
   `updateInstead` lets a push update the node's checked-out worktree directly. It refuses if that
   worktree is dirty, which is the desired safety behavior.
4. Toolchain must match: Java 21, Maven 3.9.x, Python 3.13. Verify with
   `forge_nodes.sh status` (it surfaces HEAD and jar age per node).
5. Build the jar there once: `forge_nodes.sh sync <node>`.
6. Add a row to `tools/simstats/nodes.conf` with **measured** free RAM, not installed RAM.

A torch venv (`tools/nn/.venv`) is only needed on nodes that train. Generation nodes do not need it.
